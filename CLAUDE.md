# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Goal

The goal of this project is to build an AI agent that creates UML diagrams. The agent is called **GraphiteAI**. Users describe a system in a chat and GraphiteAI answers with UML diagrams.

## Project state

Graphite AI is at an early stage (React 19, TypeScript ~6, Vite 8, Tailwind, Motion, Dexie, React Router, Vitest). The front-end shell is built (see "Front-end" below): users can create projects, open chat sessions and send messages, and view diagrams. In Settings they can configure LLM providers (Anthropic, Ollama, OpenAI-compatible). Sending a chat message starts an agentic loop on the chat's provider: GraphiteAI works on its own with tools (checking diagrams with Mermaid, reading project diagrams), its final answer's diagrams are checked before the user sees them, and the reply streams in live with a Stop button. The circle button next to the message field attaches images and files (text files, PDFs) and references project diagrams, which are sent to the model with the message. Mermaid blocks in replies are saved as project diagrams, drawn as SVG with Mermaid in the chat and on the diagram page, where the source can be edited and the SVG downloaded. The domain model from the UML class diagram in `docs/uml/` is implemented in `src/lib/` as framework-free TypeScript (no React imports), re-exported from `src/lib/index.ts`. Treat the UML as the spec when extending it.

## Development workflow

- **Test-driven development (TDD) is required.** For every feature or bug fix, write a failing test first, confirm it fails for the expected reason, then write the minimum code to make it pass, then refactor with the tests green (red → green → refactor). Don't write production code without a test that demands it.
- **Keep this file current.** After every change, update CLAUDE.md so it reflects the new state of the project (commands, libraries, architecture, conventions, project state). Include the CLAUDE.md update in the same commit as the change.

## Libraries

- **Tailwind CSS v4** via the `@tailwindcss/vite` plugin — there is no `tailwind.config.js` or PostCSS config. `src/index.css` starts with `@import "tailwindcss";`; customize with `@theme` blocks in CSS, not a JS config. Preflight is active, so the leftover template styles in `index.css`/`App.css` sit on top of Tailwind's reset.
- **Motion** (formerly Framer Motion) — import from `motion/react` (not `framer-motion`). `src/main.tsx` wraps the app in `<MotionConfig reducedMotion="user">`, so animations respect the OS reduced-motion setting.
- **Dexie** (IndexedDB) — the single database instance lives in `src/db.ts` as `db`, typed with `EntityTable`. Tables mirror the UML: `projects`, `chatSessions` (`title`, `draft`, optional `providerId`), `messages` (agent messages may carry `steps`: the `AgentStep`s the agent took before answering), `diagrams` (`type`, `name`, `source`, matching `Diagram` in `src/lib`). MessageParts are composed by their Message and stored inline in `messages.parts` (a `type`-discriminated union of `text`, `code`, `diagram-reference` (with `versionId` pinning the diagram version the message showed; missing on older references) and `attachment` (`name`, `mediaType`, base64 `data`)), not in their own table. User messages can hold attachment and diagram-reference parts; a message can be only context, with no text. The `stores()` strings list only the primary key and indexed fields. Adding non-indexed fields needs no version bump. To change indexes, add a new `db.version(n + 1).stores(...)`; don't edit the existing version.
- Diagram versions live in the Dexie `diagramVersions` table (schema version 4, indexed by `diagramId`): `{ diagramId, source, savedAt, author: 'agent' | 'user' | 'earlier', restoredFrom? }`. Order them by `id` (auto-increment), not `savedAt`, which can tie. Write diagrams only through the `src/mutations.ts` helpers, so every change of source is recorded.
- App settings live in the Dexie `settings` table (schema version 3, `{ key, value }`). The only one so far is `'agent'` (see `src/agent/settings.ts`).
- Per-browser UI preferences (sidebar width and collapsed state) use `useStoredState(key, initial, parse)` (`components/useStoredState.ts`), which reads `localStorage` synchronously so the layout doesn't flash, and ignores storage errors. Keys are prefixed `graphite.`. App data and settings that matter belong in Dexie, not here.
- **dexie-react-hooks** — components read the database with `useLiveQuery`, so the UI re-renders when any write lands (no manual refetching). A live query returns `undefined` while loading. Pages that must tell "loading" from "missing" return `(await table.get(id)) ?? null`, where `null` means not found.
- **React Router v8** (`react-router` package; there's no `react-router-dom`). Data-router style: the route table is `routes` in `src/routes.tsx`. `App.tsx` passes it to `createBrowserRouter`, and tests pass it to `createMemoryRouter`. Import everything, including `RouterProvider`, from `react-router`.
- **Mermaid** (v12): draws diagrams. Only `src/components/renderMermaid.ts` touches it. It lazy-loads the library (separate chunk), uses `securityLevel: 'strict'` (sanitized SVG, safe to inject), and picks a dark/neutral theme from `prefers-color-scheme`. Components use `useMermaid(source)` (`loading` / `done` + `svg` / `error`) and `<MermaidSvg>` to show the result, falling back to the error and source. `validateMermaid(source)` runs the same render and returns Mermaid's error message or null; the agent uses it so it sees exactly the error a user would. jsdom can't run Mermaid, so `src/test/setup.ts` mocks the module globally: `renderMermaid` returns an SVG that echoes the source (`data-testid="mermaid-svg"`) and `validateMermaid` returns null (valid). Override them per test with `vi.mocked(...)`, and reset in `afterEach` (`mockReset().mockResolvedValue(null)`) since overrides persist. `package.json` has an `overrides` entry forcing `lodash-es` to `^4.18.1`, because Mermaid 12's dependencies (chevrotain, dagre-d3-es) pin a version with security advisories. Remove the override once Mermaid ships patched dependencies (`npm ls lodash-es`).
- **@anthropic-ai/sdk**: `AnthropicProvider` uses the official SDK (not raw fetch), streaming with `client.beta.messages.stream` + `finalMessage()`, with `dangerouslyAllowBrowser: true` because the app has no backend and users bring their own key. Ollama and OpenAI-compatible providers use plain `fetch` through `src/lib/http.ts`: `request` (throws an `HttpError` with `status` and the server's message, including Gemini's array-wrapped errors), `requestJson`, `joinUrl`, and the stream readers `readLines` (NDJSON) and `readServerSentEvents` (SSE up to `[DONE]`). Before touching Claude API code, load the `claude-api` skill; model IDs, beta headers and parameters change often.

## Testing

- Vitest config is the `test` block in `vite.config.ts`: `jsdom` environment, setup file `src/test/setup.ts`. Tests sit next to their source as `*.test.ts(x)`.
- Globals are **off**: import `describe`/`it`/`expect`/`vi` from `vitest`. The setup file registers jest-dom matchers and calls Testing Library's `cleanup` after each test.
- The setup file also imports `fake-indexeddb/auto`, so Dexie runs in memory during tests. Reset state between tests with `await db.delete(); await db.open()` (see `src/db.test.ts`).
- Use `@testing-library/react` plus `@testing-library/user-event` for component tests.
- Node 25 defines its own `localStorage` (a non-working stub without `--localstorage-file`) that hides jsdom's, so `src/test/setup.ts` installs an in-memory `Storage` when the global one isn't usable. Route tests clear it in `beforeEach`. To simulate a reload, call `cleanup()` and render again.
- Agent tests (`src/agent/conversation.test.ts`) seed an Ollama provider and stub `fetch` to act as its server; type the mocks with `vi.fn<FetchLike>` so `mock.calls` type-checks. A one-line `Response.json({ message, done: true })` is a valid (single-chunk) Ollama stream, so simple stubs need no streaming; tests that watch progress build a `ReadableStream` body and push NDJSON lines themselves (`stubOllamaStream` in `src/routes.test.tsx`, which also errors the stream on abort).
- `src/agent/replies.ts` keeps in-flight replies in module state keyed by chat id. Chat ids restart after a db reset, so a test that leaves a reply running (e.g. a failing Stop test) can block later tests' replies in the same file.
- Attachment UI tests create `File`s and use `userEvent.upload(screen.getByLabelText(/attach files/i), files)` (the hidden input) or `userEvent.paste({ files })`. `userEvent` enforces the input's `accept` and doesn't understand wildcards like `text/*`, so `accept` lists explicit types and extensions. Use `userEvent.setup({ applyAccept: false })` to test files the picker would filter out.
- Page and route tests live in `src/routes.test.tsx` and `src/settings.test.tsx`. They use `renderAt(path)` and `expectPath(router, path)` from `src/test/router.tsx`, and seed Dexie directly. After any navigation (`router.navigate`, or a click followed by `expectPath`), use `findBy*` for the next query, never `getBy*`: the URL changes before React commits the new page, and the old page may still be mounted. Provider tests (`src/lib/providers.test.ts`) inject a fake `fetch` and never hit the network; it returns plain values as JSON and `Response` objects as they are, and helpers build each provider's stream (`anthropicStream` SSE events, `ndjson`, `sse`). UI tests that need network stub `fetch` with `vi.stubGlobal` and restore it with `vi.unstubAllGlobals()`. After sending, wait for the live reply to go away (`queryByRole('article', { busy: true })` is null) before querying the saved reply; otherwise the query can catch the live article just before it unmounts. Reset the db in `beforeEach`, not `afterEach`: an `afterEach` reset runs before Testing Library's cleanup, while live queries are still mounted.
- `src/lib/` tests use a stub `LlmModel` subclass (see `ChatSession.test.ts`; `AiAgent.test.ts` has a `ScriptedModel` that plays one `ModelStep` per call and records the turns it was sent). Agent replies are async, so wait with `vi.waitFor(() => expect(session.messages).toHaveLength(n))`.
- Test files are under `src/`, so `tsc -b` (and therefore `npm run build`) type-checks them too.

## Architecture (from `docs/uml/`, implemented in `src/lib/`)

`docs/uml/graphite-ai-uml.mdj` is a StarUML model; `docs/uml/Class.jpg` is its rendered class diagram. Update both if the design changes. The `.mdj` also contains stale elements that are not on the diagram (TextRenderer, RenderableAscii, Eventful, EventListener, Referencable, MessageBlock, TextBlock). Don't implement those.

`Class.jpg` shows the agentic-loop, streaming and attachment members on the existing classes: AiAgent (`options`, `attach`, `detach`, `runTool`), LlmModel (`step`), LlmProvider (`learned`), AgenticTool (`inputSchema`) and ChatSession (`reportError`, `reportProgress`). The new classes are in the `.mdj` model but not yet placed on the Class diagram: ToolCall, ToolResult, ChatTurn, TurnAttachment, ModelStep, StepOptions, AgentStep, AgentProgress, AiAgentOptions, Attachment and AttachmentKind. Until they are, the `.mdj` model is the reference for them. When editing the `.mdj` by script, keep StarUML's format (tabs, CRLF, no trailing newline) so diffs stay small, give new elements unique `_id`s, and set `_parent` refs. StarUML adds members of existing classes to their diagram boxes by itself; new classes have to be dragged in from the Model Explorer.

The domain model is an AI chat app that produces diagrams:

- **Project** composes **ChatSession**s and **Diagram**s.
- **ChatSession** holds a `draft` and composes **Message**s (`sender`, `on`, `isSent`); each Message composes **MessagePart**s (`type`, `content`). **DiagramReference** is a MessagePart subtype that points at a Diagram.
- **AiAgent** (`name`, `systemPrompt`, `respond(message)`) is attached to a ChatSession, aggregates one **LlmModel** and a set of **AgenticTool**s (`name`, `description`, `call(args)`).
- **LlmProvider** (`name`, `provideModel(args)`, `listModels()`) composes LlmModels. LlmProvider and AgenticTool implement **Parametered** (`exposeParameters()`), i.e. they describe their own configurable arguments.
- **Attachment** (in the `.mdj` model, not yet placed on `Class.jpg`) is a MessagePart subtype for a file the user attached.
- **Renderable** (`render()`) is implemented by Message, MessagePart, and Diagram. Its purpose: convert ASCII-based formats the LLM produces (JSON, XML, Markdown) into browser-native output (HTML, CSS, SVG).
- **EventEmitter** (`on`/`off`/protected `emit`) drives the chat loop: the ChatSession depends on it, and the agent learns when to respond via emitted events rather than direct calls, so multiple messages can go back and forth asynchronously.

### How `src/lib/` maps onto the UML

One file per class/interface, named after it. Places where the code intentionally differs from or adds to the diagram:

- `ChatSession` **extends** `EventEmitter<ChatSessionEvents>` (events: `message`, `draft`, `error`, `progress`); a subclass is the only way to call the protected `emit`. The agent reports through `reportError(error)` and `reportProgress(progress)`.
- UML `draft(message)` is `setDraft(message)`, because TS can't have a property and a method named `draft`. `send(message = this.draft)` marks the message as sent, stamps `on`, appends it and emits `message`.
- `AiAgent.attach(session)` subscribes to `message` and replies via `session.send(reply)`, ignoring its own messages. `ChatSession.setAgent()` handles attach/detach. Agent failures surface as the session's `error` event.
- **The agentic loop lives in `AiAgent.respond()`** and is provider-neutral. Each iteration calls `model.step(turns, tools, { systemPrompt, onText, onThinking, signal })`, which returns a `ModelStep` (`text`, `toolCalls`, optional `native`). If the step has tool calls, the agent runs them (a thrown error, missing argument or unknown tool becomes an `isError` result for the model, never a failed reply) and loops. If it has none, it's an answer: `options.checkAnswer(answer)` may return feedback, which goes back to the model as a user turn so it revises the answer (the rejected answer is never sent). Otherwise the answer becomes the reply `Message`. `options.maxSteps` (default 12) caps model calls. On the last step the model is told to answer without tools. If it still doesn't, the last answer is delivered even if unchecked, or the reply fails with "didn't finish". `options.signal` aborts between steps and is passed to the provider. The constructor is `(name, model, tools, systemPrompt, options)`. `AiAgentOptions`, `AgentStep` (`thinking`/`note`/`tool`/`check`) and `AgentProgress` (`{ steps, draft }`) are code additions not in the UML.
- Progress: every streamed text delta, reasoning delta, tool call (first pending, then with its `result`) and check is emitted as an immutable `AgentProgress` snapshot through `session.reportProgress`. Text the model wrote before calling tools becomes a `note` step; `draft` holds the current step's streaming text.
- `LlmModel` and `LlmProvider` are abstract. `LlmModel.step()` (not in the UML) is one model turn. It streams and owns the provider's wire format; it does not loop. The neutral transcript type is `ChatTurn` (`chatTurns.ts`): `user`/`assistant` text turns, assistant turns with `toolCalls` and `native`, and `tool` turns with `results`. `native` is the provider's own record of an assistant turn, replayed unchanged: Anthropic content blocks (thinking signatures must survive the tool loop) and OpenAI-style wire tool calls with extra fields (Gemini's `extra_content.google.thought_signature` is required on replay, or Gemini returns a 400). `AgenticTool.inputSchema()` gives the JSON Schema every tool-calling API takes.
- `LlmProvider.listModels(args)` takes the same args as `provideModel` (the UML shows no parameters). Settings uses it to suggest model names. Its constructor takes `{ fetch }` so tests can inject a stub. `learned(key, initial)` returns a mutable record of what's been found out about a model (keyed by server URL and model name), shared by every model object for it. The app creates a new provider and model per reply, so it lives in module state, kept per `fetch` function: the default fetch is one shared function, so real replies share it, while each test's fake fetch gets its own. `withDefaults(args)` fills in parameter defaults, and `requireArgs(args)` also throws on missing required settings; `provideModel` uses `requireArgs`.
- Concrete providers: `AnthropicProvider`, `OllamaProvider`, `OpenAiCompatibleProvider` (OpenAI, OpenRouter, Groq, LM Studio, ...). Each file also holds its private `LlmModel` subclass, which maps `ChatTurn`s to its API and streams:
  - Anthropic: SDK stream, `max_tokens: 64000`, `tool_result` blocks in a user message. It throws if `max_tokens` cuts off a tool call.
  - Ollama: `/api/chat` with `stream: true` (NDJSON), `message.thinking` as reasoning, `{ role: 'tool', tool_name }` results. Ollama tool calls have no ids, so ids are generated. A model that "does not support tools" is retried without tools (remembered through `learned`); its answers are still checked.
  - OpenAI-compatible: SSE, tool-call pieces assembled by index, `reasoning_content`/`reasoning` as reasoning. It accepts a plain JSON completion from servers that ignore `stream`. Unparseable tool arguments become `{}`. Servers differ in what they accept, so a 400 makes it step down and retry, remembering the result through `learned`: an error mentioning tools or functions drops `tools`; otherwise, if the turns hold PDFs, the PDF format goes from OpenAI's `file` part to an `image_url` data URL (what Gemini's endpoint accepts) to no PDF plus the note. Other errors are thrown as they are.

  `toChatTurns(history)` maps stored Messages to text turns: sender `'user'` is the user, anyone else is the assistant. `DiagramReference` parts become fenced ```` ```mermaid ```` source, so the model sees (and can revise) earlier diagrams; in user turns they get a `Referenced diagram "<name>":` label. Attached text files are inlined as `Attached file "<name>":` plus a fence (longer than any backtick run inside). Images and PDFs become the turn's `attachments` (`TurnAttachment`), and each provider maps them: Anthropic `image`/`document` blocks before the text; Ollama `images` (images only); OpenAI-compatible `image_url` data-URL parts, with PDFs as described above. Ollama, and OpenAI-compatible servers that accept neither PDF format, get `unreadablePdfNote()` in the text instead. Only the current reply's tool transcript is sent; earlier replies are replayed as text (no thinking blocks), which is safe for Anthropic's preserved-thinking check because blocks are only ever dropped from the front.
- `retitle(source, title)` sets or adds the Mermaid frontmatter title (quoting it when YAML needs that). Renaming a diagram in the UI uses it, so the agent, which matches diagrams by title, keeps finding the renamed diagram.
- `diffLines(before, after)` (`diffLines.ts`): a longest-common-subsequence line diff (`same` / `removed` / `added`; within a change, removed lines come first), used to compare diagram versions.
- `parseReply(text)` (`parseReply.ts`) splits a Markdown reply into `text`, `code` and `diagram` segments. A ```` ```mermaid ```` block is a diagram named by its frontmatter `title:`; `diagramTypeOf()` maps the Mermaid header keyword to a UML type (`class`, `sequence`, `state`, `er`, `activity`, else `mermaid`).
- The Anthropic model sends `fallbacks: "default"` (beta `server-side-fallback-2026-07-01`) only for `claude-opus-5` and `claude-fable-5-1`, and throws on `stop_reason: "refusal"`. After a mid-output fallback it drops `thinking`/`redacted_thinking`/`tool_use`/`server_tool_use` blocks that come before the last `fallback` block (text stays), both from `native` and from the returned tool calls. It sends `thinking: { type: 'adaptive', display: 'summarized' }` (so reasoning summaries can be shown) only to models matching `ADAPTIVE_THINKING` (Opus 5/4.6–4.8, Sonnet 5/4.6, Fable 5, Mythos 5); others such as Haiku 4.5 reject it. Top-level `cache_control: { type: 'ephemeral' }` turns on prompt caching, so each agent step (which resends the history and any attachments) mostly reads from the cache. Default model: `claude-opus-5`. `eager_input_streaming` is deliberately off: tool inputs are small and the UI doesn't show them streaming.
- `Attachment` (`Attachment.ts`): `{ name, mediaType, data }` with base64 `data` and a computed `kind` (`attachmentKind()`): `image` (PNG, JPEG, GIF, WebP: `IMAGE_TYPES`), `pdf`, or `text` (`text/*`, JSON/XML/YAML/SQL types, or a known source/text extension, since browsers often give no media type). The constructor throws for anything else, and for data that isn't plain base64, because image data goes into a `data:` URL. `text()` decodes UTF-8; `render()` gives an escaped `<img>` or file name. `toBase64(text)` encodes UTF-8.
- `AgenticTool` is concrete, built from `{ name, description, parameters, handler }`, and `call()` validates required args. Parameter shape: `Parameter` in `Parametered.ts`, which adds optional `secret` (mask it in UIs) and `default` to the UML.
- `render()` returns an HTML string. Always pass LLM-produced text through `escapeHtml` (`Renderable.ts`). `MessagePart` renders `text` as Markdown with `renderMarkdown()` (`markdown.ts`: a small subset covering paragraphs, headings, lists, quotes, rules, tables, emphasis, inline code and http(s)/mailto links; everything is escaped first) and `code` as an escaped `<pre>`, and `Diagram.render()` (which adds a `source` field) returns its escaped source, because Mermaid rendering is async and lives in the UI layer (`renderMermaid`).

## Agent (`src/agent/`)

The app-side glue between Dexie, providers and the `src/lib` agent. It is React-free.

- `systemPrompt.ts`: `AGENT_NAME` (`'GraphiteAI'`, the sender of agent messages) and `SYSTEM_PROMPT`. GraphiteAI draws diagrams as titled Mermaid blocks in its final reply, so any model can produce them, even without tool calling. A diagram output again with the same title (case-insensitive) replaces the stored one. The prompt tells it to work on its own first (look at project diagrams, check every diagram) and reply only when satisfied.
- `tools.ts`: `diagramTools(projectId)` returns GraphiteAI's tools. `check_diagram(source)` runs `validateMermaid` and throws Mermaid's error, so the model sees it as an error result. `list_diagrams()` lists the project's diagrams from all chats. `read_diagram(title)` returns a diagram's current source (case-insensitive title). `checkDiagrams(answer)` is the agent's `checkAnswer`: it validates every mermaid block of a finished answer and returns feedback naming each broken diagram and its Mermaid error. The user never sees a diagram that fails to render unless the step limit runs out. `sameName()` is the shared title comparison.
- `conversation.ts`: `sendMessage(chatSessionId, text, context = [])` stores the user message: its text (if any) followed by the `ContextPart`s (attachment and diagram-reference records). Diagram references are pinned to the diagram's current version (`currentVersionId`). It names a `NEW_CHAT_TITLE` chat after the text, or else after the first attachment or diagram, then calls `reply(chatSessionId)`. A message with neither text nor context isn't sent. `reply` answers only an unanswered last user message, and does nothing if the chat already has a reply in progress. It loads the history and project diagrams and runs them through a `ChatSession` + `AiAgent`, with `diagramTools`, `checkDiagrams` and an abort signal. The agent reacts to the session's `message` event, following the UML. Progress events go to `replies.ts`. The reply is saved with `parseReply`: diagrams are upserted by name into the project and referenced from the message, pinned to the version the reply created (`versionId`), and the final `steps` are stored on the message (omitted when empty). It remembers the provider on the chat (`providerId`). With no provider configured it throws `NoProviderError`. Provider errors propagate to the caller. The step limit comes from `loadAgentSettings()`. A stopped reply resolves quietly: if the agent had already written some answer text (`progress.draft`), that is saved as the reply with `stopped: true`, and its diagrams are kept as `mermaid` code parts (they never passed the Mermaid check, so they don't become project diagrams). If nothing was written yet, nothing is saved.
- `replies.ts`: replies in progress, outside React, so a reply keeps streaming and can still be stopped after the user leaves the chat. `replyProgress(chatId)`, `subscribeToReplies(listener)` and `stopReply(chatId)` are for the UI; `startReply` (returns null if one is already running), `updateReply` and `endReply` are for `conversation.ts`.
- History as the model sees it: each diagram reference shows its pinned version, re-titled with the diagram's current name (`retitle`), because the agent finds diagrams by title and would otherwise recreate a renamed one. Unpinned (older) references show the current source. If a diagram has a newer version than the last one shown in the chat (for example, you edited its source), the last user turn gets a note with its current source (`outsideChangesNote`). The note is only sent to the model, not stored.
- `settings.ts`: `AgentSettings` (`maxSteps`), `DEFAULT_AGENT_SETTINGS` (12), `MAX_STEPS_RANGE` (1–50), `loadAgentSettings()` and `saveAgentSettings()` (rounds and clamps).
- `chatTitle.ts`: `NEW_CHAT_TITLE`, `titleFrom()`.
- If the chat is deleted while a reply is in flight, the reply is dropped (checked inside the save transaction).

Cross-table writes live in `src/mutations.ts`. Cascading deletes: `deleteProject` (chats, messages, diagrams and their versions), `deleteChat` (messages; diagrams stay in the project) and `deleteDiagram` (its versions; messages keep the reference and show "Diagram deleted"). Diagram versions: `createDiagram(diagram, author)` adds a diagram with its first version and returns `{ diagramId, versionId }`. `currentVersionId(diagramId)` gives the newest version's id, recording an `earlier` version first for a diagram from before version history. `updateDiagramSource(id, source, author, restoredFrom?)` sets the source and the type it implies, then records a version; saving the same source again records nothing. It returns the version that's current afterwards. A diagram from before version history first gets its old source recorded as an `earlier` version. `restoreDiagramVersion(versionId)` makes an old version current again as a new `user` version, re-titled with the diagram's current name. Renaming (`retitle`) doesn't add a version. The agent (`saveReply`) and the diagram page write through these, so their transactions include `db.diagramVersions`.

## Front-end (`src/routes.tsx`, `src/pages/`, `src/components/`)

The main user journey starts on the projects page. Inside a project, the user works with chat sessions and diagrams. The layout follows the user's wireframe: a sidebar on the left, a top bar, and the chat in the middle, with agent messages on the left, user messages on the right, and the input bar at the bottom. Pages use tighter padding below the `sm`/`md` breakpoints (e.g. `px-4 sm:px-6`), and chat bubbles are wider on phones (`max-w-[88%] sm:max-w-[80%]`). jsdom applies no CSS, so check layout changes in a browser at phone width (a same-origin 390px `<iframe>` of the app works when the window can't be resized).

| Path | Component | What it shows |

- The provider kinds a user can configure are listed in `src/providers.ts` (`providerKinds`: label, description, factory). To add a provider, write the `LlmProvider` in `src/lib` and register it there. Configured providers live in the Dexie `providers` table (schema version 2): `{ kind, name, args }`.
- Renaming and deleting: `EditableTitle` (pencil button "Rename {noun}"; Enter/blur saves, Escape cancels) and `ConfirmDelete` (trash button "Delete {noun}", then an inline "Yes, delete"/"Cancel"; no browser dialogs). Projects are renamed and deleted from the project top bar, chats from a slim header in `ChatPage`, and diagrams from the `DiagramPage` toolbar. After a delete, the page navigates to the parent.
- `AppHeader` (brand + Settings link) tops the projects and settings pages. Inside a project, Settings is at the bottom of the sidebar.
- Messages from sender `'user'` are the user's. Any other sender is treated as the agent (`data-sender="agent"`).
- Style `renderMarkdown` output with `markdownStyles` (`components/markdownStyles.ts`), applied to the text part's `RenderedHtml` only, so it doesn't leak into diagram cards. `ChatPage` stays scrolled to the bottom while async content (diagram previews) grows, via a `ResizeObserver` that is skipped in jsdom, unless the user has scrolled up.
- Render LLM content through `src/lib` Renderables with `<RenderedHtml of={...}>`, never as raw strings. The exception is diagram SVGs, which come from Mermaid's strict mode (see Libraries). `MessagePart` and `Diagram` escape their input. Style the generated markup with Tailwind arbitrary child variants (`[&_pre]:...`).
- Styling uses Tailwind only, with a zinc ("graphite") palette. Dark mode uses `dark:` variants, which follow the OS setting. There are no component CSS files; `src/index.css` holds only the Tailwind import and base styles. The logo mark is `components/Logo.tsx`, and `public/favicon.svg` is the same mark.
